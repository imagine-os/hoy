## Smallest dependency-safe repair recommendation

**Only existing checked_in→booked Undo**, with an explicit mock-only command and safe lifecycle. Leave new booking, mark-arrived, mark-no-show and no_show→checked_in semantics visible as separate current flows/gaps; do not add direct no_show→booked Undo while its seat semantics remain undecided.

1. Snapshot exact actor/provider/context, target booking/session revision and original live callbacks/AbortSignal before awaits. Require current checkin.write under the existing four roles, a fresh active tenant actor, and a freshly tenant-owned booking still checked_in in the same selected tenant session. Preserve recipient identity and booking fields. The current roster can show a booking without a matching Person/profile (`!x.p` at67 and fallback user_id at198); do not invent a requirement for an active subject customer/profile merely to undo historical attendance. The actor's current authorization and the owned booking/session are the required rows.
2. Preserve the actual reachable time contract: no new before-start, end-of-class, same-day or grace-period ban. Scheduled/completed noncancelled occurrences can remain eligible whether future, in-progress or past. Invalid/missing/foreign/ambiguous required rows are a technical verification failure, not a newly invented business time policy. A fresh cancelled session is not exposed by the current page and must not accept a new stale Undo; a committed historical receipt can be acknowledged against its still-owned valid target without executing another transition.
3. The provider must distinguish an **occupancy-neutral undo** from new admission: same existing booking ID/tenant/user/session, checked_in→booked, same mat and only the status+checked_in_at change. A positive allowlist or dedicated contained attendance transition may be necessary because calling data.update currently invokes prepareBooking. Do not bypass provider validation through a page-level db mutation/proxy or relax prepareBooking's start/status/capacity/duplicate/mat checks for insert, changed user/session/mat, cancellation resurrection or no-show readmission. Root must reconcile the narrow provider change with batch42's actual integrated admission implementation before coding/merging this part.
4. Stage booking status booked + checked_in_at null and the existing booking.undo audit together. Preserve ledger/payment/purchased terms/mat/session identity, all other booking history fields and existing audit source/action/role semantics. Let the adapter derive occupancy as it already does; no manual count decrement or no-show policy rewrite. A valid full class retains its occupied seat. Missing/invalid/conflicting legacy mat/capacity history must not be silently assigned/repaired; any unprovable case is explicitly unverified pending root's concrete contract review.
5. Use a stable scoped nonce/fingerprint receipt containing IDs/hashes/allowlisted historical outcome, no names, notes, contacts or raw roster body. Fresh active actor/owned target/session checks are required inside the new transaction and around replay/postcommit acknowledgement; do not rely solely on the generic atomic callback-skipping replay path. Exact retry after time advances must not update checked_in_at again, add another undo audit or resurrect a row after a newer check-in. Changed payload, missing/reassigned required rows and stale status conflict honestly. Cancel/lost acknowledgement after commit cannot claim rollback.
6. Replace only the S02 Undo action composition with loading/read-error/retry/immediate busy/stop/unmount/selection/actor/provider fences, retaining the command through uncertain acknowledgement. Avoid locking only the former arrived button after it moves to Expected; prevent a conflicting next attendance action until the owned outcome is known. Existing check-in/no-show actions can remain separately identified gaps; no declaration of complete RC02 atomicity. All new actual widget states must have matching provider-free D02 usages, EN/ES and D01 tokens when implementation is authorized.

This is a proposed contract for root review, **not runtime authorization**. Batch45 eventual release depends on checked main70 and batch42 provider changes. Direct generic provider/table-entry bypass and real server role/tenant isolation remain explicitly unverified; a fictional helper cannot establish a universal authorization guarantee.
