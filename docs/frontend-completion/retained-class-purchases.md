# PG-09 · Feature Log 62 · source row 63

The original Plans reproduction committed one simulated purchase, lost its acknowledgement, then reloaded and retried with a new in-memory UUID. A second approved payment and package grant resulted. The misleading error also asserted no classes had activated.

The replacement class-purchase contract stores a tenant/customer-scoped attempt and frozen quote. Candidate row IDs are retained before transaction commit, so a missing transaction receipt with surviving payment/grant evidence cannot be treated as a fresh purchase. Recovery validates exact persisted identity, immutable receipt/quote and one original purchase grant. Supported freeze/resume and canonical customer/studio cancellation returns are recognized without changing those rules or records. Current catalog terms are irrelevant to an already committed result.

Plans and Classes load and recover read-only, present saved terms and an unsent saved receipt, and require an explicit payment retry, result acknowledgement or proven-uncommitted cancellation. Stale retry controls never create a fresh ID. Context changes cancel continuation, while the original scoped marker survives for later recovery. Unreadable or inconsistent proof remains blocked.

`test-retained-class-purchase.mjs` covers 23 command groups: staged/marker/storage failures, replay, context changes, exact proof corruption, legitimate subsequent history and explicit new purchases. The 32-group development suite uses actual pages and a dev-only context harness that is absent from application routes/build imports. A separate compiled suite covers ten native purchase/recovery journeys, including two dark-theme cases, with no browser source or test imports. Its test-only lost-acknowledgement fault wraps the actual mock provider instance after durable commit. It fails explicitly if that instance cannot be identified.

The full build and the existing nine-group rendered quotation regression passed. Quotation tests wait for the actual failed storage write before restoring the fault and acknowledge one recorded result before intentionally starting another purchase; amount, grant, replay and rollback assertions remain. The eight source-mapped receipt paths remain domain evidence rather than native page evidence. A dedicated read-only CI workflow retains these domain, development and compiled gates. Local screenshots are generated under `docs/screenshots/retained-class-purchase/` and `docs/screenshots/retained-class-purchase-native/`.

Limits: frontend MockProvider/current dataset only. Daily demo resets, real server/processor settlement, authenticated durable idempotency and cross-device concurrency are not certified.
