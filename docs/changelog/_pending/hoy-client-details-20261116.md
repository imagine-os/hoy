# HOY client details — unreleased, 16 November 2026

Prompt intent: Jas needs to open an existing client, view details and edit them. The production CRM list had no row navigation, while its existing detail route already supplied history, payments and payment void actions.

Decision: keep review mode and the existing client history/payment surface unchanged, adding a production-only personal-details editor within that existing page using the authenticated tenant-bound DataProvider request seam. A client must have exactly one accessible member facet linked to the requested person. Editing is limited to name, phone, birthday and emergency contact. Email, login links, roles, pricing, memberships, payments and bookings are not written. Each changed field is compared against its read value inside one idempotent batch; confirmation comes from a fresh person/member read. Read-only roles and view-as do not receive an editing action. Route identity uses only CompanyOSProvider.self(): the current login and its person share the original display identity while the personal editor always receives the raw person id. Other people are never inferred from contact details. Identity responses are invalidated on provider, actor, role, view-as, permission or route changes.

Alternative rejected: replace the existing client surface and lose its history/payment/void actions, or broaden teacher permissions while enabling client editing.
