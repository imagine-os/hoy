# Hoy test environment: the passphrase gate on test.hoyhumanclub.com (Company OS playbook rule D5)

Prompt intent: the owner's rule (2026-11-03): every customer's test environment lives at `test.<customer domain>`, behind a passphrase, because Hoy's test site was open on a Railway-generated address (Company OS tech-debt #79). For Hoy, `test.hoyhumanclub.com`, the whole site gated.

Decision:
- `server/testGate.mjs` is the D5 contract on `node:http`, no new dependency, and runs first in the handler: on only with `TEST_GATE_PASSPHRASE`, never with `RAILWAY_ENVIRONMENT_NAME=production`; a passphrase without `COOKIE_SIGNING_SECRET` answers 503; no valid cookie is a 401 passphrase page (plain HTML, Spanish and English, no app bundle) or 401 JSON under `/api/`, `/files/` and `/private-docs/`; the cookie is signed over the origin, the passphrase's hash and the expiry, `HttpOnly`, `Secure`, `SameSite=Lax`, 30 days; 5 wrong tries in 15 minutes from one address, then 429, in a bounded in-memory count; `next` is a path on this site only; every answer says noindex while it is on.
- Exempt, exactly: `/health` and `POST /webhooks/resend`. Hoy's emails (`src/notifications/launchEmails.ts`, `deploy/comms/hoy-templates.json`) load no image from the site, so no image path is exempt.
- The limiter counts the edge's `X-Real-IP`, as everywhere else in the server, not the first `X-Forwarded-For` hop, which a browser can write and rotate to get more tries (accepted change from the plan). An IPv6 address counts as its /64, since one customer holds a whole /64; an IPv4 address written as IPv6 counts as that IPv4 address.
- On any Railway environment but production, the server refuses to start without `TEST_GATE_PASSPHRASE` and `COOKIE_SIGNING_SECRET`, so a passphrase removed by hand can't silently open the site. Only `test` and `production` deploy this server (the wiring test checks it). The half-configured 503 stays for a server started away from Railway.
- `deploy-test.yml` ends with `scripts/smoke-test-gate.mjs`, which fails the run: `/health` reaches this commit (bounded, 5 minutes), `/` answers 401 with the form, `/api/cos/x` answers 401 `test_gate`, and six wrong passphrases each claiming another `X-Real-IP` end in 429, which proves the edge overwrites that header. It is given no passphrase.
- Static files answer `private` instead of `public` in `Cache-Control` while the gate is on, so no shared cache hands them past the gate.
- The app tells the gate's 401 from a dead session (`src/auth/testGateReload.ts`, used by `transport.ts`, `cosRequest.ts`, `ProductionSession.tsx`, `privateDocs.ts`): it reloads the page so the server shows the passphrase page, at most once a minute per tab, and doesn't tell the session. New refusal copy for `test_gate`.
- A write that meets the gate does not reload, so nothing typed is lost: the form stays and shows the `test_gate` copy (reads and boot still reload; `POST /query` counts as a read). A reload goes to the top page when it is same-origin, so a frame of the Hub's DeviceFrame never lands on the gate page's `frame-ancestors 'none'`; a cross-origin parent makes the frame reload itself. Without a reload (a write, the guard window, no storage), `/me` and the docs show the `test_gate` copy instead of a session problem or "signed out".
- The by-hand `real-signup` job takes the site's address from the `test` environment's `APP_URL` (one variable, no separate `HOY_TEST_URL`) and passes the gate first when `TEST_GATE_PASSPHRASE` is set (`passGate`, `withGateCookie` in `scripts/lib/real-signup.mjs`): the cookie goes on its fetches, its clean-up client and its browser.
- `deploy-switches.mjs --production` warns about a `TEST_GATE_PASSPHRASE` left on production.
- A browser run (`scripts/test-test-gate-ui.mjs`, in the `fake-clerk` job) proves the same-origin cookie end to end: passphrase page, app, a signed-in call that reaches a fake Company OS.
- The app's calls to its own server go from `credentials: 'omit'` to `'same-origin'` (`src/data/companyos/transport.ts`, `src/auth/cosRequest.ts`, `src/auth/ProductionSession.tsx`, `src/modules/docs/privateDocs.ts`). With `omit` the gate's cookie never travels, so every call would answer the gate's 401 on the test site. Identity stays the bearer: the server reads no other cookie and forwards none.
- `deploy-test.yml`: `APP_URL` comes from the `test` environment's variable, with no fallback to the Railway domain (the `railway domain` call is gone); the deploy fails before any Railway change without `APP_URL`, `TEST_GATE_PASSPHRASE` (at least 12 characters) or `COOKIE_SIGNING_SECRET` (at least 32); both secrets are synced and the bundle scan looks for both. `deploy-prod.yml` refuses a `TEST_GATE_PASSPHRASE` secret. `.railway/railway.ts` declares `COOKIE_SIGNING_SECRET` in both environments and `TEST_GATE_PASSPHRASE` on test only.

Known limits:
- The passphrase page keeps the path and query but not the `#/…` part of an address, which never reaches the server: a first visit through a deep link lands on the home page. It happens once per browser every 30 days.
- The smoke check leaves the GitHub runner's address blocked for 15 minutes; nobody else uses it.
- On a re-run of a commit already live, the smoke check's count can restart if the deployment switches mid-check, so its sixth try can answer 401 with a sound edge. The error says to run it again first; telling the two apart would need the Railway CLI in the step.

Alternative rejected:
- Exempting `/api/` from the gate so the app's calls could keep `credentials: 'omit'`: D5 gates API paths, and the signed-out website's reads would be open to anyone.
- An inline script on the passphrase page to carry the `#/…` part through the form: the page stays plain HTML with a CSP that allows no script.
- Keeping the Railway domain as a fallback address: a deploy would then succeed with Clerk's `azp` and the cookie's origin bound to the wrong site.
