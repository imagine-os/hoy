# Frontend CMS contract maintenance

The adopted registry covers three feature groups: monetary gift C-17, package purchase C-06 / C-07b, and transfer review S-09 with its related M-03 table evidence. It does not certify every page, runtime behavior, backend compatibility or live synchronization. Backend entity/field mappings remain pending. The current provider emits browser-local events.

Descriptors live in `src/cms/features/`; `src/cms/registry.ts` discovers the files present in each branch. Keep the shared contracts, registry, checker and fixtures identical across independent feature branches. Each branch may register only its own descriptor; integration combines the descriptors. Do not introduce another filter/sort engine: page view preferences use the existing `TableViewConfig` from `src/data/schema.ts`. Gift is a form and preview, packages use cards and a ledger list, and transfer review is a review list. These flows do not become tables merely because the inventory is called CMS.

For every change to an adopted feature, update the following together:

1. Its descriptor: actual route/spec/component, render kind, consumed fields, command effects, identity links, tenant/actor context, states, and per-section view configuration where relevant.
2. Entity mapping status: keep unresolved remote mappings explicitly pending. Local field names do not establish a remote schema or authorization policy. Browser-only field/enum extensions require a type, source path and explanation; they do not alter the draft database schema.
3. Its fictional samples in `src/cms/fixtures.ts`: preserve stable `id`, `tenant_id`, timestamps and correct field types/enums. These bounded samples demonstrate contract shapes; they do not replace feature behavior tests or application seeds.
4. Its actual provider tests: review whether the existing tests cover the changed behavior, extend them when necessary, and retain their path, hash and purpose in `adapterTests`. Update `reviewedSourceDigest` only after that review. This metadata does not claim a test was executed.
5. The descriptor revision and source fingerprints, including new helpers, consumers and test dependencies introduced by the change. Run `npm run check:cms` and the relevant existing feature/provider checks. Record actual results in the feature's normal delivery evidence.

The TypeScript descriptors and fixtures contain one JSON block between `cms-data:start` and `cms-data:end` comments. Keep that block strict JSON. The dependency-free checker reads it without executing app code, starting a browser, loading TypeScript or connecting to a service. Source/test hashes are lowercase SHA-256 of the file bytes. The source review digest is SHA-256 of the sorted `path:sha256` source entries joined by a newline (no trailing newline; ordinary lexical path order). Each fixture and provider-test review carries that digest. A source change therefore requires an explicit descriptor, fixture and test-adequacy review. Do not refresh hashes as an automatic build step or merely to suppress a failure.

`npm run check:cms` validates the descriptors present in the branch against the local source, schema, route/spec binding and bounded samples. Unknown runtime fields require explicit browser-only extensions. It validates the sample fields, not full seed completeness or every expression inside a component. Source fingerprints detect changes to declared files; contributors must include newly introduced helpers and relevant test dependencies. Static checks cannot decide whether a behavior assertion is adequate.

`node scripts/check-cms-contracts.mjs --self-test` exercises an isolated valid contract and negative cases without running application tests. The CMS workflow runs for pull requests and pushes to main, checks out the exact event commit with read-only repository permissions, installs locked dependencies, then runs both checks. The normal build starts with `npm run check:cms`, so the existing Pages build also enforces the inventory. Feature workflows remain responsible for actual provider/domain/browser tests. Run a full build at the coordinated integration gate, not as part of this cheap inventory check.

Before merging, the author or integration owner must validate the combined preview against then-current main. Independent parallel drafts can each pass while their combination changes shared source files, fixtures or provider tests. Reconcile the affected source fingerprints, fixture digests and test-review metadata after reviewing that combined change, then rerun the CMS check and relevant feature gates. Never refresh hashes silently or treat a passing isolated draft as evidence that the combined preview passes.

Saved table views remain `table_views`; section ordering remains `page_layouts`; sidebar conveniences remain the existing table preferences. This foundation introduces no new persistence or runtime repository. The existing `useTable` / `useRow` async error and stale-result limitations remain unresolved here. Future repository consumers must provide explicit loading/error/retry states, context-aware identity, latest-result protection, subscription cleanup and honest transport capabilities. A future remote adapter must be separately designed and verified before any connected behavior is claimed.
