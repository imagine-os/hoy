## Logic and integrations
- No card data touches our servers — gateway tokenisation only; PCI DSS SAQ-A scope.
- Cash creates a pending order that the front desk settles; booking holds 60 minutes.
- Electronic invoicing per DIAN requirements; receipt includes NIT and IVA breakdown.
- Refunds return to the original method; credits are refunded as credits.
- Habeas Data (Ley 1581) consent recorded before storing any method.
- Integrations: WhatsApp, Wompi, Email, DIAN e-invoicing

## States
- Loading: rows shimmer
- Empty: 'Add a payment method'
- Gateway down: cash/transfer only + banner
- Expired card: inline warning

## Real vs mock
- **Real.** Saved methods are `payment_methods` rows the member fully controls: add, remove, make
  default. The row shape — provider, kind, brand, last4, expiry — is the shape Wompi will fill, and the
  PAN never reaches HoyOS. The manual methods (transfer, cash at the desk) are real alternatives that
  create pending `payments` the front desk settles in S-04, and they remain available whatever happens
  to the gateway.
- **Mock / pending.** `token_ref` is a visible demo placeholder (`tok_demo_…`) produced by
  `wompiTokenise()`; the real widget returns `tokenized_card.token` and replaces it without changing
  the row. The card test charge goes through the simulated `wompiCheckout()`. Nothing is vaulted,
  because there is no vault yet.
- **Transfer instructions.** The payout account, account type and holder are stored in M-08c, so the
  transfer instructions can read the studio's real account instead of hardcoded text. Teacher payouts
  now use the same account from the other direction (M-09a).
